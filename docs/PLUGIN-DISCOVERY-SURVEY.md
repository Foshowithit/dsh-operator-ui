# DSH community plugin discovery survey

Survey note for the capability-library planning packet. Observations below were made on **2026-09-28**. Disposition and source-boundary language follows the [plugin ecosystem contract](PLUGIN-ECOSYSTEM-CONTRACT.md). This is a bounded source survey and candidate shortlist, not an audit of either directory, an installation test, or a compatibility/security review.

## Findings and source coverage

The [dshfind home](https://dshfind.com/) describes a community learning and plugin directory. Its [marketplace page](https://dshfind.com/en/plugins) says entries are public GitHub repositories under the `dsh-plugin` topic and shows **16,141 plugins** on the page captured for this survey. The current [API guide](https://github.com/hikariming/dshfind/blob/6be2b8f653595483e14303e457afe97affd4548d/docs/api-query.md) documents REST, GraphQL, a catalog endpoint and a DSH catalog-source manifest; a one-row API probe plus `/healthz` returned **16,312 total records** on 2026-09-28 (dataset version `sha256:113dd0ff…`; 16,312 loaded). These are source-reported totals, not counts independently audited here; the page/API discrepancy is a freshness or publication-state difference to preserve, not reconcile by guess. The guide says GitHub sync is daily, the in-memory snapshot refreshes about every 10 minutes, and exposes `as_of`/`data_version` for freshness and consistency. The API and its deployed contract were not independently certified for long-term stability in this survey.

dshfind has a documented machine-readable REST and GraphQL interface, a full-catalog JSON endpoint, and a standard catalog manifest plus cursor-paginated pages. Its documented stable identity is `full_name` (`owner/repo`); multi-page reads can pin `data_version`, use ETags and restart on stale-page responses. The API also explicitly describes `is_plugin` as tri-state and scores, categories, editorial flags, and install probes as dshfind-derived fields—not GitHub facts. Its docs warn against using the marketplace-specific first-wave/200-entry response as a full catalog. **The API is documented, but I found no explicit catalog-data reuse license or terms in that guide; check rights before automated enumeration or ingestion.** The one-row count/status probe above was a bounded survey observation, not a bulk catalog read. A public endpoint and a license on source code do not by themselves license reuse of catalog data.

The [awesome-dsh-plugin site](https://awesome-dsh-plugin.com/) was too large for the web reader, so I did not crawl its pages. Its public [robots.txt](https://awesome-dsh-plugin.com/robots.txt) points to a sitemap; the site’s [count endpoint](https://awesome-dsh-plugin.com/count.json) reported **4,382 plugins**, with `Last-Modified: 2026-09-28 16:37:19 GMT` (site-reported, not audited). The linked primary source is [awesome-dsh-plugin/awesome-dsh-plugin at `4c4167f`](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/tree/4c4167fa0dc992395f8d9c56cfb27e1f812ddb33): its README is a curated list, its stated inclusion bar is install-and-description checking rather than quality ranking or security review, and it warns that a listed plugin runs with the user's machine permissions. The repository declares CC0-1.0, has per-entry YAML under `data/plugins/`, and publishes a documented static [`plugins.json`](https://awesome-dsh-plugin.com/plugins.json) feed. On the survey date that feed had 4,382 entries and was explicitly documented by [dsh-market at `42e55f0`](https://github.com/dsh-market/dsh-market/tree/42e55f03c883fc301374436a534eceb398f70f33) as its live catalog source. **Count this as one catalog with two provenance references** (upstream feed and downstream Market view), not as two independent sets of 4,382 listings. The feed is a whole-catalog static document, not a versioned/paginated API; it lacks a schema version and stable record ID. The repository's CC0 applies to its own work, not linked plugin code; retain each project’s license separately.

The directories likely overlap because dshfind indexes the GitHub `dsh-plugin` topic and awesome-dsh-plugin lists community repositories, but the overlap has not been measured by matching a complete snapshot. dsh-market is a view over the same awesome feed; count that feed once and preserve both provenance references without assuming differently timed snapshots contain identical rows. Preserve source-specific metadata even when rows point to the same repository. These are discovery sources only. This product’s roadmap requires a canonical capability record, typed execution binding, prerequisites, evidence, independent evals, provenance, and honest readiness states before a task capability becomes selectable. A third-party host plugin is not an Operator capability or permission grant.

## Complete-disposition plan

1. **Freeze source observations.** For dshfind, first resolve catalog-data reuse rights and API terms; do not run bulk enumeration while they are unknown. If cleared, record retrieval time, `data_version`, `as_of`, reported total, response ETag and pinned API-document revision. For awesome-dsh-plugin, pin the CC0 repository commit and static `plugins.json` response; record response validators/time, repo license and count consistency. Keep site counts publisher-reported. Record dsh-market as a downstream view/provenance reference to the same awesome feed, not a second collection.
2. **Acquire bounded snapshots, then deep-review.** After the dshfind rights gate, acquire at most 100 rows per API batch, pinned to one `data_version`; for awesome, read one pinned whole-catalog `plugins.json` snapshot (or bounded source-file batches if the snapshot cannot be validated). Do not enumerate live detail pages. Deep-review 25 rows at a time. Every source row keeps its source key or a source-local locator, listing URL and retrieval revision/time; do not invent a cross-source stable ID.
3. **Keep product treatment separate from evidence state.** Assign only the K2 dispositions `native-reuse`, `optional-host-plugin`, `task-pack`, `ui-enhancement`, `duplicate`, `defer`, or `reject`. Record evidence state/reason separately, including `unresolved` when identity, compatibility, license, or behavior is unclear. An unresolved row stays visible and cannot be described as reviewed to completion. Do not make the K2 choice itself imply plugin audit or capability readiness.
4. **Reconcile source rows and preserve provenance.** Count the awesome feed once even when the dsh-market view surfaces it; retain both the feed reference and Market observation on each relevant row. For each pinned snapshot, reconcile fetched source-row count against that source’s reported count and the rows assigned a K2 disposition; report malformed, absent, or unresolved evidence separately. Until every batch has this accounting, say “survey in progress,” not “all listings audited.”
5. **Deduplicate without erasing provenance.** Normalize a GitHub repository URL for comparison, retaining any monorepo subpath. Preserve each source’s key/locator, descriptions, timestamps, compatibility claims and links as distinct evidence. A repository match does not authorize merging source records or prove identical capability behavior; follow the ecosystem contract and surface ambiguous matches. Keep forks, renames, package-only entries and conflicts unresolved until a human resolves them.
6. **Gate capability consideration separately.** For any candidate, check the plugin’s own license, declared DSH range, source, permissions and dependencies. Test exact supported DSH versions in isolation before recording tested compatibility. Only a separately reviewed input/output contract, real execution binding, provenance, evals and refusal cases can make a candidate eligible for a canonical Operator capability. Never auto-install or execute community code from discovery.

## Survey limits and unresolved items

This pass reviewed dshfind’s home and marketplace totals, its current API guide and one-row live status probe, selected listings, and the awesome-dsh-plugin count/robots/sitemap, pinned source structure, CC0 license, documented static `plugins.json` feed and selected entries. It did not traverse all categories/files, resolve all external repositories, audit code or permissions, or evaluate licenses/terms per plugin. dshfind’s live API and page totals differed on the observation date; bulk enumeration remains blocked on rights/terms confirmation, so complete three-source coverage cannot be claimed while it remains unresolved. The awesome feed is a documented dataset, but not a versioned or paginated API; its mutable shape still needs snapshot validation and pinned reconciliation. dsh-market reads that same feed, so its listings are a second provenance reference rather than added inventory. Compatibility, package availability, project health and security remain unknown except where a source explicitly claims them.

## Downstream blockers surfaced by plan review

- **K1 coverage:** dshfind’s API is technically enumerable, but the source contract finds no catalog-content reuse grant. Until a rights decision exists, retain `traversalComplete=false` and manually reviewed links; do not bulk-fetch its 16K-plus records. The awesome feed is the only currently documented/licensed bulk source, but has no schema revision, pagination, or stable entry ID; a pinned body digest plus source-local row locator and count reconciliation are required.
- **K3 evidence boundary:** the ecosystem contract’s `ExternalPluginListing` is metadata only. A discovery projector can show source assertions and links, but cannot join host observations, canonical links, installed state, or tested compatibility. Leave those states absent/unknown until a separate host-owned observation producer exists.
- **P1 source prerequisite:** the plan correctly blocks real-component rendering until A1 pins the actual ModuleLoader React/ReactDOM resolution and supported host source. The desktop source audit says the target `0.2.0-rc.1` archive/runtime path is still unproved (local capture is `0.1.7-rc.2`), and current component harnesses are not a browser-render proof. Preparation can proceed. Synthetic rendering needs the pinned resolver proof; actual Desktop compatibility additionally needs the exact A2 package/runtime tuple. These are separate gates.

The reviewed DAG now makes one journey depend on an existing D1/D2 pack **or** K4. K3 is also specified as a metadata-only projector. I found no remaining mismatch on those two points; the source-rights and P1 resolver blockers above remain concrete gates.
